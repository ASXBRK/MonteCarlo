# Surplus and Deficit Allocation

Conventions per CLAUDE.md, including the conservation rule: this phase moves
money between existing pockets rather than creating new flows, but the
routing changes — extend `randomScenario()` to generate allocation plans and
verify the invariant still holds, in the same commits.

**Four commits, gated.**

## Why

`settings.surplus` currently offers three whole-of-surplus choices: spend,
invest to one nominated asset, or accumulate in cash. Real advice splits the
surplus — *$1,000/month extra to the mortgage, $500 to super, $500 to the
portfolio, the rest to cash*. The most common recommendation an adviser
makes is the one the model cannot express.

The firm's workbook and Xtools both do better, and the forum research
records two rules worth adopting outright (`docs/reference/xtools-calm-reference.md`,
§3): **pay non-deductible debt first**, and **interest-rate ordering**. On
the deficit side, Xtools carries a **minimum balance** per asset group and a
**minimum capital gain** sell-down rule.

Where we should exceed them: their allocation is limited to two surplus
periods and three deficit periods, which the forum shows users complaining
about repeatedly. We have Key Dates, so ours anchors to named events with no
period limit.

**The design constraint that matters:** percentages, a remainder, ordering
rules and time periods together are a lot of state that can disagree. The
remainder must always be explicit and always reconcile — the interface must
be incapable of displaying an allocation that does not total 100%.

## COMMIT 1 — Allocation model and the engine

### State
```
settings.surplus = {
  periods: [ SurplusPeriod ],        // ordered, contiguous, cover the projection
}

SurplusPeriod = {
  id,
  from, to,                          // DateRef — Start/End/Retirement/key dates
  payNonDeductibleDebtFirst: bool,   // default TRUE
  debtOrder: "interestRate" | "manual",   // default interestRate (descending)
  allocations: [ { id, targetType, targetId, pct } ],
  remainderTo: "cash" | "expenditure",    // default "cash"
}
```
`targetType` is one of `asset` · `liability` · `superContribution` · `goal`.
For `superContribution` the `targetId` names an existing contribution row,
and the allocation tops it up — it does not create contributions implicitly.

### Rules, in the order the engine applies them each FY
1. Resolve the period covering this FY.
2. If `payNonDeductibleDebtFirst`, direct surplus to non-deductible
   liabilities before any other destination, ordered by `debtOrder`, until
   they are repaid. **Deductibility is a percentage** (`deductiblePct`), so
   rank by non-deductible proportion rather than a boolean, and treat a
   part-deductible loan proportionally.
3. Apply the remaining percentages to their destinations.
4. Anything left goes to `remainderTo`.

Repayments to a liability stop at its balance; the excess falls through to
the next destination rather than being lost. Contributions respect existing
caps — an allocation to super that would breach the concessional cap fills
to the cap and the excess falls through, rather than creating excess
contributions the client did not ask for.

### Deficit side
```
settings.deficit = {
  order: [ assetId ],                     // existing, unchanged
  minimumBalances: { [assetId]: amount }, // NEW — leave this much before moving on
  sellRule: "order" | "minimumCapitalGain", // NEW, default "order"
}
```
- **Minimum balances**: deficit funding draws an asset down to its minimum
  and then moves to the next. Only when every asset is at its minimum does
  it draw below them, in the same order, before unfunded cashflow. State
  this fallback explicitly — a plan should exhaust its buffers before it
  fails, but it should still fail visibly rather than silently ignoring the
  minimum.
- **Minimum capital gain**: sell from the asset with the smallest unrealised
  gain as a proportion of value first, recomputed each time. Pooled cost
  bases already exist, so this is a comparison rather than new machinery.
  Assets with no CGT (cash, lifestyle) sort first since selling them
  realises nothing. This is tax-aware drawdown and Xtools has no equivalent
  that is user-selectable per plan.

### Migration
Existing `{ mode, assetId }` maps to a single period covering Start→End:
`spend` → 100% remainder to expenditure; `invest` → 100% to that asset;
`accumulate` → 100% remainder to cash. **Regression gate: bit-identical
projections for every migrated scenario.**

Tests: each rule in isolation; non-deductible ordering with a part-deductible
loan; overflow falling through when a liability is repaid or a cap is hit;
minimum balances respected then breached in order; minimum-capital-gain
selection recomputed as balances change; migration bit-identity; conservation
invariant with allocation plans generated by `randomScenario()`.
Commit: `Surplus and deficit allocation: model and engine`

## COMMIT 2 — Allocation UI

Settings section, replacing the current surplus control.

- **Periods** as a list, each with From/To anchor selects. Adding a period
  splits at a chosen anchor; periods are always contiguous and always cover
  the projection — the UI must make gaps and overlaps impossible rather than
  validating them after the fact.
- Within a period: the two rule toggles, then a repeatable allocation list
  (destination select, percentage), then the remainder line.
- **The remainder is computed and always visible**: "Remainder: 35% → Cash".
  Entering percentages that exceed 100% is prevented at input, not flagged
  afterwards. There is no state in which the allocation does not total 100%.
- Deficit block: the existing ordered list gains a minimum-balance field per
  asset and the sell-rule select, with one line explaining what minimum
  capital gain does.

Show the resolved effect for the current year beneath the period —
"$2,340/month: $1,400 to Home loan, $600 to Super, $340 to Cash" — so the
percentages are legible as dollars without leaving the screen.

Commit: `Surplus and deficit allocation: settings UI`

## COMMIT 3 — Outputs

- **Cashflow table**: the Funding group breaks the surplus into its
  destinations, one row each, replacing the single "surplus invested" line.
- **Liabilities table**: surplus-driven repayments appear distinctly from
  scheduled and extra repayments, since they are a different decision.
- **Where the money went**: surplus allocation is already inside the existing
  buckets, but the waterfall should show it — worth checking the
  decomposition still reconciles exactly after this phase and saying so.
- **Focus → Surplus allocation**: a new view showing, year by year, where
  the surplus actually went, plus a comparison against a single-destination
  alternative. This is the view that answers "should we put it all on the
  mortgage or split it?" — which is the question the feature exists for.

Commit: `Surplus allocation: outputs and Focus view`

## COMMIT 4 — Non-deductible-first as an advice signal

Small, and the point of the whole phase.

When `payNonDeductibleDebtFirst` is on and the client holds both deductible
and non-deductible debt, surface the benefit explicitly: the interest saved
versus the same surplus applied pro-rata across all debt, over the
projection. One figure and one sentence, in the Focus view.

Do **not** frame it as a recommendation. State what the difference is and
why — non-deductible interest is paid from after-tax income, deductible
interest is not — and let the adviser draw the conclusion. This follows the
locked non-prescriptive convention: the tool shows what the data reveals, it
does not label a winner.

Commit: `Surplus allocation: non-deductible-first benefit`

## Deferred — do not build
Per-person surplus splitting (the workbook allocates per client; ours is
household-level and that is a deliberate simplification for now — disclose).
Allocation to entities. Automatic rebalancing between assets. Surplus
allocation inside Monte Carlo paths beyond what falls out of the
deterministic rules. Debt recycling as a named strategy — it becomes
expressible once loan drawdowns and this allocation model coexist, but it
deserves its own treatment.
